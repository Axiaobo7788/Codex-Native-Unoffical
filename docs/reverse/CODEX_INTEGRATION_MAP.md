## 1. Correction on `thread/startAeon` & `thread/environmentReady` (`STATIC_BUNDLE` `@1168648`, `@1647000`)

In the initial reverse-analysis pass, `thread/startAeon` and `thread/environmentReady` were listed alongside standard `thread/*` RPCs without isolating their execution target.
**Verified Facts (`early-bootstrap-920`)**:
1. **`thread/startAeon` (`@1168648`)**:
   ```javascript
   method: "durable" === k && "aeon" === E ? "thread/startAeon" : "thread/start"
   ```
   - `k` is the host kind (`"local" | "ssh" | "durable"`), and `E` is the product SKU (`"aeon"` when `X-OpenAI-Product-Sku: "aeon"` is set on the Durable Cloud Host WebSocket `wss://codex-cloud-backend.chatgpt.com/`).
   - `thread/startAeon` does **not** exist in local stock `codex app-server 0.167.0-alpha.3.2` (`in_stock_app_server_schema: "not_in_local_stock_schema"`). It is a **cloud-only RPC** (`PRIVATE_INTERNAL_SERVICE`).
2. **`thread/environmentReady` (`@1647000`)**:
   - Sent by `tpp-local-executor.reportReady(threadId, environmentId)` exclusively to the Durable Cloud Host (`ei.iwv`) via `sendAppServerExtensionRequest("thread/environmentReady", {threadId, environmentId, selectedCapabilityRoots})` after the local `codex exec-server` connects to the Noise rendezvous relay.
   - It is also a **cloud-only extension RPC** (`PRIVATE_INTERNAL_SERVICE`).

## 2. The Four Execution Hosts in `AppServerConnectionRegistry` (`STATIC_BUNDLE`)

ChatGPT Desktop's main process (`early-bootstrap-920`) manages four distinct `app-server` host connection types behind a single `AppServerConnectionRegistry`:

1. **`local` (`StdioAppServerConnection`)**:
   - Spawns `/opt/codex-desktop/resources/codex app-server --listen stdio://` (`PUBLIC_SUPPORTED`).
2. **`ssh:<host>` (`SshAppServerConnection`)**:
   - Spawns system `ssh` with Multiplexing (`ControlMaster=auto`, `ServerAliveInterval=15`), ensures remote `codex` CLI is installed/updated, and pipes `codex app-server` over SSH stdio (`PUBLIC_SUPPORTED` binary protocol over standard OpenSSH).
3. **`durable` (`DurableCloudAppServerConnection`)**:
   - Connects to `wss://codex-cloud-backend.chatgpt.com/` with ChatGPT Bearer auth and optional `X-OpenAI-Product-Sku: "aeon"` (`PRIVATE_INTERNAL_SERVICE`).
4. **`remote-control:<id>` (`RemoteControlAppServerConnection`)**:
   - Connects to a paired remote desktop's `codex app-server` via OpenAI's WHAM Remote Control relay (`wss://chatgpt.com/backend-api/wham/remote/control/server`) (`PRIVATE_INTERNAL_SERVICE` on controller/relay side; `EXPERIMENTAL_STOCK_SCHEMA` on host side).

A critical correction to `ADR-031` is that **"Official Remote Control" is not a single monolithic block**. When stratified into its 8 actual architectural layers, the **Host-side control plane** is already part of stock `codex app-server` (`PUBLIC_SOURCE` `--experimental`), whereas the **Controller-side enrollment & cloud relay** are `PRIVATE_INTERNAL_SERVICE`:

### Architectural Consequence: Keep `RemoteBackend` Dual-Track (`ADR-032`)
Instead of `ADR-031`'s premature decision to permanently lock in `Direct Host` as the sole primary Remote architecture and dismiss official Remote compatibility, `ADR-032` establishes a **dual-track `RemoteBackend` abstraction**:
1. **Track A — `DirectHostRemoteBackend` (`PUBLIC_SUPPORTED` / Self-Hosted Primary for Unofficial Android-to-Desktop)**:
   - Uses our Rust `codex-native-host` resumable WebSocket bridge (sequence/ack replay, pairing, `512 MiB/item` & `2 GiB/session` large-output spool) or SSH/Tailscale tunnel to stock `codex app-server`. Zero dependency on OpenAI's private `/wham/` relay or `step_up_token`.
2. **Track B — `OfficialRemoteControlHostAdapter` (`EXPERIMENTAL_STOCK_SCHEMA` on Desktop Host / `RESEARCH_MORE` on Controller)**:
   - On Desktop, we can optionally expose stock `codex app-server`'s `remoteControl/status/read`, `remoteControl/enable`, `remoteControl/pairing/start`, and `remoteControl/client/list` (`PUBLIC_SOURCE` `--experimental`) so users who use the official ChatGPT mobile/desktop controller can pair with their local `app-server` right from our UI!
   - Controller-side cloud relay connection remains `RESEARCH_MORE` until/unless public controller enrollment exists.
